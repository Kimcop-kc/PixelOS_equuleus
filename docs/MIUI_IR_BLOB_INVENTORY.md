# MIUI_IR_BLOB_INVENTORY — what the factory firmware actually contains

Source firmware: `equuleus_images_V12.5.2.0.QECCNXM_20211118.0000.00_10.0_cn_4ce136c735.tgz`
(Xiaomi Mi 8 Pro, China, Android 10, MIUI 12.5.2).

Extraction date: **2026-11-12**. Host: Windows 11 + Git-bash + WSL `debugfs`.

## 2. IR-related components found

### 2.1 OV9282 sensor stack (the IR camera)

| Path (vendor-relative) | Size | Notes |
| --- | --- | --- |
| `lib/camera/com.qti.sensor.ov9282.so` | 28,288 | sensor driver module |
| `lib/camera/com.qti.sensormodule.ov9282.bin` | 39,101 | module/slot descriptor |
| `lib/camera/com.qti.tuned.ofilm_ov9282.bin` | 379,825 | tuning data (OFILM module) |

The OmniVision OV9282 is a 1 MP global-shutter **monochrome** sensor — the IR
camera on this device. Its presence here confirms the sensor is driven through
Qualcomm's CAMX sensor-module mechanism, not through a vendor-specific daemon.

### 2.2 Camera HAL and face detection

| Path | Size | Class |
| --- | --- | --- |
| `lib/hw/camera.qcom.so` | 3,275,248 | ELF32 (machine 40 = ARM) |
| `lib/libcamxfdengine.so` | 86,480 | ELF32 |
| `lib/libcamxfdalgov7.so` | 1,555,848 | ELF32 |
| `lib64/libcamxfdengine.so` | 110,912 | ELF64 |
| `lib64/libcamxfdalgov7.so` | 1,652,648 | ELF64 |
| `lib/libmmcamera_faceproc.so` | 1,246,516 | ELF32 |
| `lib64/libmmcamera_faceproc.so` | 1,312,512 | ELF64 (see §3.2) |

All sizes above are taken from `logs/miui-ir-compare.json`, which is
generated by `scripts/compare_ir_blobs.py` from the actual files. The
32-bit and 64-bit builds of the same library differ in size; do not
copy one row's value into the other.

`camera.qcom.so` is a **32-bit** HAL. That matters: it decides which of the two
`libmmcamera_faceproc.so` builds is actually loaded.

### 2.3 MIUI face-unlock stack (MIUI framework, NOT reusable)

| Path | Note |
| --- | --- |
| `lib/libFaceGrade.so` | MIUI face grading |
| `lib/libstfaceunlockoclqcom.so` | ST face-unlock OC wrapper — **absent from LineageOS** |
| `lib/libscveFaceRecognition.so` | Qualcomm SCVE face recognition |
| `lib/libscveFaceLandmarks.so` | Qualcomm SCVE landmarks |
| `etc/scve/facereco` | SCVE face recognition data |
| `etc/camera/face_{goodly,ravishing,splendid}_*` | MIUI beauty/face models |

These implement *MIUI's* face unlock. They are not a drop-in for ParanoidSense:
they are called by MIUI's own framework services, which do not exist in
PixelOS. Per the task constraints they are **not** to be declared
PixelOS-compatible, and no SELinux or authentication requirement is bypassed to
make them load. See `IR_FACE_UNLOCK_DEPENDENCIES.md` §4.

### 2.4 IR illumination — NOT VERIFIED

**Status: NOT VERIFIED. The control mechanism is unknown.**

Two completely different things on a phone are called "IR". They must not be
conflated:

| Thing | What it is | This device |
| --- | --- | --- |
| **IR blaster** (consumer IR) | an emitter used as a TV/remote control, driven through the Android `ConsumerIr` HAL | **not present.** No `consumer_ir` / `consumerir` / `ir_blaster` reference anywhere in the device tree, and no consumerir HAL binary in the vendor dump |
| **IR illuminator** (face unlock) | an emitter that lights the user's face so the OV9282 monochrome sensor can image it in darkness | the hardware exists (OV9282 is the IR camera); **how it is switched on is unknown** |

These are unrelated subsystems. The absence of a consumer-IR blaster says
nothing either way about the face-unlock illuminator.

#### What the static files do and do not show

Searched, and found **nothing**:

| Searched for | Where | Result |
| --- | --- | --- |
| `/sys/class/leds/*ir*`, `ir_led`, `ir_illum`, `illuminat` | all of MIUI's `vendor/etc` | no match |
| `flood`, `duty`, `pwm` (illuminator drive terms) | `vendor/etc/camera/` | no match |
| a consumerspace LED control node for the emitter | MIUI vendor dump | no match |

That absence is **not** evidence that no control exists. It only means no
userspace configuration file in the vendor partition names it. Three mechanisms
remain possible and were **not** distinguished by static analysis:

1. driven implicitly by the OV9282 sensor module when a stream is opened in the
   IR configuration (no separate userspace control at all),
2. driven by a kernel driver / device-tree `leds` or GPIO node, which would live
   in the kernel or DTB — **not in the file sets examined here**,
3. driven through a CAMX vendor tag written by the HAL.

**Which one applies is NOT VERIFIED.** Determining it requires either a booted
device (observe whether the emitter lights when the IR camera is opened, and with
which configuration) or the kernel source / DTB for this device, neither of which
was inspected in this round.

#### Consequence for debugging, stated as a hypothesis only

If IR frames are dark, the possible causes are unresolved: wrong camera id (the
RGB sensor has no emitter), the sensor not opened in the IR configuration, an
emitter that is genuinely not being driven, or an emitter control path outside
the vendor partition entirely. No ordering is claimed.

#### What would settle it

```bash
# on a booted build, with the IR camera opened:
ls -l /sys/class/leds/
cat /sys/kernel/debug/gpio | grep -i ir
dmesg | grep -iE "ir_|ov9282|flood"
# then block the illuminator with tape and retry unlock in the dark:
#   if unlock still succeeds, the pipeline is not using IR at all
```

That last test is in `IR_FACE_UNLOCK_DEPENDENCIES.md` §8 as test 5 and is the
only reliable discriminator; nothing in this document should be read as a
finding about runtime behaviour.

## 3. Files that are NOT byte-identical to LineageOS

Only two of the eighteen interest-set paths differ, and neither requires a
change to the device tree.

### 3.1 `lib/libmmcamera_faceproc.so` — 3 bytes

| | |
| --- | --- |
| Size | 1,246,516 (identical) |
| Differing bytes | **3** at offsets `0x7Fe0`, `0x7FE2`, `0x7FE4` |
| MIUI value | `0x03, 0x03, 0x03` |
| LineageOS value | `0x01, 0x01, 0x01` |

Those offsets are in the ELF **symbol version** table, and `0x03 → 0x01` is
exactly what `device/xiaomi/equuleus/extract-files.py` does:

```python
'vendor/lib/libmmcamera_faceproc.so': blob_fixup()
    .clear_symbol_version('__aeabi_memcpy')
    .clear_symbol_version('__aeabi_memset')
    .clear_symbol_version('__gnu_Unwind_Find_exidx'),
```

So this is **not** an MIUI-vs-LineageOS content difference. It is LineageOS's
deliberate, documented fixup applied to the same MIUI blob. The LineageOS copy
is the corrected one and must be kept as-is.

### 3.2 `lib64/libmmcamera_faceproc.so` — MIUI-only

MIUI ships both a 32-bit and a 64-bit `libmmcamera_faceproc.so`. The LineageOS
blob list requests only `vendor/lib/libmmcamera_faceproc.so`
(`device-xiaomi-equuleus/proprietary-files.txt:153`), which is the copy the
**32-bit** `camera.qcom.so` loads. The 64-bit copy is therefore unreferenced and
adding it would be dead weight.

### 3.3 `bin/hw/android.hardware.camera.provider@2.4-service` — MIUI-only

A prebuilt service binary in MIUI. LineageOS/PixelOS **build this from source**
(`sdm845.mk:105` adds `android.hardware.camera.provider@2.4-service`, provided by
`hardware/interfaces`). Shipping MIUI's prebuilt copy would shadow the
source-built one and is not done.

## 4. What this inventory establishes

* The factory firmware is verified against Xiaomi's own md5 manifest.
* Every component the IR camera needs is present in MIUI's `vendor`.
* The two apparent differences are explained: one is LineageOS's own fixup, the
  other two are unreferenced/build-from-source artifacts.

## 5. What was deliberately not extracted

`system.img` (3.14 GB) was not unpacked. The IR camera path is entirely inside
`vendor` on this platform: the sensor module, its tuning data, the camera HAL and
the face-detection libraries are all present in the `vendor` dump, and the
partitions are separate filesystems with no cross-partition dependency for
camera blobs. Extracting 3.14 GB to search for a duplicate would not change any
conclusion here.

If a future question needs it, the same `simg2img.py` → `debugfs` sequence
applies, and `system.img`'s md5 is in the extracted `md5sum.xml`.

## 6. Reproduce

```bash
# integrity
gzip -t equuleus_images_V12.5.2.0.QECCNXM_20211118.0000.00_10.0_cn_4ce136c735.tgz

# extract the images we need
gzip -dc …tgz | tar -x --wildcards "*/images/vendor.img" "*/md5sum.xml"

# verify against Xiaomi's manifest
md5sum images/vendor.img      # must equal the value in md5sum.xml

# unsparse, then dump (read-only)
python3 scripts/simg2img.py images/vendor.img images/vendor_raw.img
debugfs -R 'rdump / ./dump/vendor_miui' images/vendor_raw.img

# compare against the LineageOS extraction
python3 scripts/compare_ir_blobs.py ./dump/vendor_miui . --json logs/miui-ir-compare.json
```
